# 飞书进度同步

把跨来源材料压缩成对收件人有用、事实边界清楚且可安全发送的进度消息。

## 依赖与身份

- 私聊、群聊读取和发送使用 `lark-im`。
- 姓名解析和同名消歧使用 `lark-contact`。
- 会议和妙记使用 `lark-meeting`；云文档使用 `lark-doc`。
- 默认使用 `--as user` 读取用户可见材料并以用户本人身份发送。只有用户明确要求应用机器人发送时才用 `--as bot`，且必须确认机器人已具备目标会话可见性。

## 工作流

### 1. 锁定范围

确定进度主体、材料来源、时间范围、收件人和发送渠道。能从当前上下文可靠获得时不重复询问；时间范围不明确时优先读取最近一周，并在草稿中标明截至时间。

读取只限于用户指定的人、群、会议或主题。不要因为拥有最大权限就扩展搜索到无关私聊、群聊或文档。

### 2. 解析会话和人员

1. 按姓名搜索联系人；私聊优先使用返回的 `p2p_chat_id` 或对方 `open_id`。
2. 搜索结果有多名同名人员且下一步要发送时，展示候选的姓名、邮箱和部门，让用户选择；禁止擅自选第一条。
3. 已知 `open_id` 时可用联系人接口回查姓名和邮箱，确认身份后直接交给 `lark-im`。

### 3. 读取证据

按时间升序读取目标聊天，需要完整正文时使用 JSON 格式和自动分页。发现线程且线程内容影响结论时再展开；图片或附件只有在其内容是关键证据时才下载。

跨会议或文档取证时保留来源边界。聊天中的提议、口头认可和正式完成不是同一状态，不因对方回复“好”就推断任务验收完成。

### 4. 建立进度账本

把每项内容归入一种状态：

- `已完成`：存在结果、产物、已运行实验或明确验收。
- `部分完成`：有阶段结果，但样本、稳定性、审核或交付未闭环。
- `已对齐/已决定`：双方明确同意方向或优先级，但执行尚未完成。
- `下一步`：将要做的工作，不写成成果。
- `阻塞/待确认`：缺接口、权限、数据、负责人或决策。

保留数字的样本、时间和适用范围。不要转发寒暄、玩笑、情绪表达、与收件人无关的私人信息或原始长聊天记录。

### 5. 面向收件人改写

默认结构为简短开场、3–6 条进度、下一步或协作需求。首次使用缩写、内部代号或专业术语时说明其含义和当前作用。明确哪些是双方共识、哪些是发送者判断、哪些仍待对方确认。

敏感信息最小化：不包含应用密钥、访问令牌、open_id、chat_id、文档 token、内部授权链接或没有必要的个人信息。内部仓库名称可以写，但不附访问凭证。

### 6. 发送确认

发送前必须让用户确认三项：

1. 唯一收件人或目标群。
2. 将要发送的完整正文。
3. `user` 或 `bot` 发送身份。

如果用户的当前请求已明确给出三项并确认正文，可直接发送；仅说“整理一下”或正文由 Agent 新生成时，先展示草稿并等待“确认发送”。

### 7. 发送与验证

摘要、标题和列表使用 Markdown 消息。使用稳定、无敏感信息的幂等键，避免一小时内因重试重复发送。成功必须满足 `ok=true`，并向用户返回收件人、发送身份和 `message_id`；失败时保留准确错误，不自动切换身份、收件人或群聊。

发送后的消息属于外部状态。除非用户明确要求且接口允许，不编辑、撤回、加急或转发该消息。
