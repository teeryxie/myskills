# dstack 多机多卡训推提交

将已授权的作业提交到正确的执行入口，保留可核验的代码、数据和作业标识。先区分平台资源生命周期、常驻 worker 生命周期和队列子作业生命周期。

## 使用边界

- 本 skill 不提供停止、删除、替换常驻任务或创建 GPU 集群的操作。用户要求复用集群时，使用现有队列；不要把独立 dstack 多节点 task 当作已有集群的子作业。
- 创建 0 GPU 辅助任务也是一次资源申请，说明其 CPU、内存、挂载、时限和目的。已有会话授权涵盖提交所需辅助任务时继续执行，不重复索要许可。若用户禁止任何新任务，不能用 CPU 任务绕过限制。
- 没有 SSH 时不要猜测 SSH 可用，也不要擅自操作网页。按当前平台提供的 CLI/API、共享挂载或现有命令执行入口选择路径。不要把不存在的远程 exec 接口当作已有能力。
- 只清理本子作业创建的进程组；保留 supervisor 的退出清理。读取 `DSTACK_NODE_RANK` 等上下文不等于管理集群。
- token 只从会话授权的凭据环境或配置读取，不写入 skill、仓库、上传包、任务命令或运行清单。

## 按需读取

- 涉及上传、计划或入队：读 [提交接口](references/submission.md)。附带脚本仅打包和上传文件，不申请运行资源。
- 出现失败、长时间无日志或需要判断是否真的开训：读 [排障与验证](references/diagnostics.md)。
- 当前项目为 Telos/WLC 或 scope：读 [已验证案例](references/telos-wlc.md)。里面的路径和状态是有日期的实例，使用前核实，不当作所有项目默认值。

## 提交前最少核实项

1. 从当前 checkout、远程 Git、平台运行状态和队列实际文件收集证据。核实目标项目、常驻任务、预期节点及每节点 GPU 数、当前 active job、队列位置和提交脚本。
2. 对比代码变动后再同步；远程被 force-push 时先检查两侧提交与 diff，保留已授权的安全修复和用户新增内容。不直接 reset、force-push 或恢复被删除的资源配置。
3. 按实际内容确认训练/评测数据、样本数、唯一 prompt 数和重复情况。文件名不能证明用途。至少比较去空白/大小写规范化后的 prompt；结构相似、语义近似的泄漏需要另行分析。尊重用户明确的实验划分，发现新重叠时说明含义。
4. 核实本地权重版本及必要文件，多个快照时显式选择。共享路径存在不等于当前 worker 已挂载，也不等于所有节点可读。
5. 固定角色依赖、CUDA/PyTorch/算子兼容性、GPU 分工、数据路径、输出预算、训练步数或服务运行方式。角色拆分与 GPU 比例由项目需求决定。

## 运行准备

- 优先复用项目已有启动和队列脚本，不额外建立调度系统。审核实际提交脚本，确认发布 READY 前先写完脚本和元数据。
- 训练、图像生成、评分等冲突依赖按角色隔离。共享安装目录用实际跨节点生效的锁；NFS `nolock,local_lock=all` 上不要假设 `flock` 是分布式锁，可用原子 `mkdir` 配合有界等待。
- 安装锁超时先查 owner；不能因等待时间长就删除锁。复用已验证环境时核实依赖摘要，运行期间不就地升级共享环境。
- 版本目录保存固定 commit 的代码与数据。若复用可变 venv/本地库，记录其依赖摘要；这不等于环境完全不可变。输出以队列 job ID 隔离。
- 多节点启动核实 rendezvous、网卡、端口、健康检查及异常传播。不要把 `eth0`、InfiniBand 或节点数硬编码为跨平台通则。
- 长驻推理服务还要确定 endpoint、鉴权、健康检查和服务结束语义。串行队列中的无限服务会持续占用队列，不能套用有限训练作业的完成条件。

## 执行与回执

没有共享卷直连入口时，可以在授权范围内通过短时 0 GPU 任务部署代码并提交已有队列。其时限只作用于辅助任务，不能传播成 GPU 常驻任务的生命周期设置。

1. 在本地构建并验证上传包，审查明确选择的文件。上传成功仅代表平台接受文件。
2. 在执行环境里先校验包、代码版本、数据哈希、权重和环境，再提交队列。检查失败不得写 READY。
3. 每次外部提交前本地记录唯一请求名和用途；响应后立即记录 dstack run ID。网络超时或 apply 响应丢失时，先按请求名查询，不能盲目重试。
4. 队列提交返回 job ID 后持久化回执。辅助任务后续失败不代表队列提交失败。检查 queue、running、archive 和结果目录，确认无重复后才考虑再提交。
5. active 文件缺失可能是空闲或状态切换；单次 `cat` 失败不能触发重提。作业从 queue 消失也可能是被领取了。

## 结果表述

明确区分：文件已上传、辅助任务已接受、正式作业已入队、worker 已领取、服务已就绪、模型/优化器已初始化、首步已完成、有效更新已验证、完整运行已完成。

训练需要实际 loss/梯度、组内奖励差异、截断比例、吞吐、显存和产物证据。GRPO 的零 loss 单独不能判定故障；持续零梯度或零奖励方差也不能宣称学习成功。推理需要真实请求输出及跨节点服务证据，健康检查不代表吞吐已验证。

最终报告包含正式 job ID、代码版本、输出位置、已确认阶段、未验证项以及现有资源是否变更。不要将 `running` 或 smoke 成功等同于完整训练有效。

## 持续改进

用户要求完善 skill 时，以实际日志和可复现行为做窄范围修改：记录日期/平台版本、触发条件、错误、修复、验证结果和仍未知项。仅是假设的原因明确标注，不升级成固定规则。

优先顺序：先修脚本可复现缺陷并加离线行为测试，再更新对应参考；只有跨任务成立的决策才进入本文件。不要复制 token、长日志或将单次资源配比固化为普遍要求。没有用户请求时不自动改写记忆、不建立后台巡检。

本地验证：运行 `scripts/test_bundle.py`、脚本 `--help`，并用可用的 skill 校验器验证 frontmatter。离线测试不得提交真实资源；真实平台验证使用当前授权范围，并单独报告它验证了哪个阶段。
